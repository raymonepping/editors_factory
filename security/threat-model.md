# Threat Model

## What this project demonstrates

> An autonomous actor with a valid identity can still cause damage when
> access, trust, and delegated authority are badly bounded.

Not: "look how dangerous Ollama/OpenAI/Claude is." The model provider is
architecturally irrelevant here on purpose — see
`prompts/base_project/04_01_ollama_model_runtime.md`. Every action Agent
C takes in BAD mode is one that succeeds because **identity worked,
authentication worked, Vault worked, PostgreSQL worked, and the agent
worked** — nothing was hacked, nothing malfunctioned. The failure is that
Agent C had more authority than the task required.

## What this project explicitly does not attempt to prove

- Not a red-team/pentest of any real LLM vendor.
- Not a claim about model alignment, "AI safety" in the alignment-research
  sense, or model refusal behavior.
- Not a general-purpose agent-framework security product.
- Not a demonstration of prompt injection or jailbreaking (the model's
  own reasoning is trusted to be locally rational throughout; the flaw
  being demonstrated is in the surrounding authority architecture, not in
  tricking the model into misbehaving).

## AI agent security: why the boundary holds even though prompt injection isn't the focus

The section above rules out prompt injection/jailbreaking as something
this project sets out to *demonstrate*. It is worth being explicit about
why the architecture is resilient to it anyway, as a side effect of
design choices made for other reasons — an external review of this
project (`input/VALIDATION.md`, `input/Navi_Validation.md`) asked this
to be documented directly rather than left implicit:

- **Capability boundary, not behavioral boundary.** An agent cannot
  select a tool it was never given — the tool schema itself is the
  boundary (`prompts/agents/0*`), not a system-prompt instruction the
  model could be talked out of.
- **No agent holds a credential to talk anyone out of.** An attacker
  cannot manipulate Agent C to leak or misuse a database password directly,
  because Agent C never holds a Vault token or database credentials; see
  `security/authority-model.md`'s "Why agents do not hold Vault
  credentials directly."
- **Authority is intersected server-side, not asserted by the agent.**
  A delegation envelope cannot grow because an agent (truthfully or
  under adversarial influence) claims it should
  (`prompts/backend/01_01_orchestrator_api.md`).
- **Vault Sentinel adds a layer the agent's own output never reaches.**
  `require-agent-c-for-db-creds` (`prompts/base_project/02_02_vault_follow_up.md`)
  is evaluated on the backend's short-lived child token metadata (`token.metadata["factory_agent"] == "agent-c"`),
  not on anything an agent said — no amount of convincing Agent C changes the child-token
  metadata minted by the backend broker.

A successfully "convinced" Agent C still cannot exceed its actual
granted authority, because that authority is never a function of what
Agent C believes, decides, or is told. This is a *consequence* of the
project's core architecture, not a separate control bolted on for this
paragraph.

## Blast-radius boundary

Everything the demo can possibly damage is enumerated in
`security/authority-model.md`'s "Containment rules" section, and is
limited to:

```text
The Factory's own PostgreSQL database (synthetic products/orders/
inventory/suppliers data, seeded deterministically)
```

Nothing else — not the host machine, not any other project on the same
machine, not any real credential, not any database outside the synthetic
factory schema. Model inference runs 100% locally on Ollama. While general
outbound internet egress is not firewalled at the host network driver level in
this local setup, no agent workload requires external connectivity. If a
future prompt proposes giving any agent container host-level mounts, sockets, or
non-`factory-*` Vault credentials, that proposal must be rejected or explicitly
re-scoped through this document before implementation.

## Secrets hygiene for this repository

- Vault Enterprise license files (`vault-s/config/*.hclic`) are never
  committed — see `prompts/base_project/02_01_vault_ha_cluster.md`.
- `.env` values are real local-dev material and are git-ignored;
  `.env.example` documents shape only.
- `.secrets/vault/`, `.secrets/terraform/` (Terraform local state for
  `terraform/vault-platform/`, `terraform/vault-sentinel/`,
  `terraform/vault-database/`), and `vault-tls/` (generated by
  `scripts/vault-prepare.sh`) are local, git-ignored state — never
  captured wholesale into `state/` baselines
  (`prompts/process/00_01_state_recording_baseline.md`'s whitelist rule
  applies here without exception).
- `FACTORY_VAULT_ROLE_ID`/`FACTORY_VAULT_SECRET_ID` in `.env`
  (`prompts/base_project/02_02_vault_follow_up.md`): `role_id` alone is
  not sensitive (AppRole's two-factor design), `secret_id` is — both
  still live only in the git-ignored `.env`, never in `terraform/` state
  or `.tf` files.
- Per-agent bearer tokens
  (`prompts/backend/01_01_orchestrator_api.md`'s agent-auth scheme) are
  generated at stack bring-up, never hardcoded into a committed file.
- Run `commit_gh --scan` (or the project's equivalent secret scanner)
  before every commit that touches `compose/`, `.env*`, or `scripts/`.

## Repeatability and safety requirements (non-negotiable)

Carried forward from the original design conversations
(`input/09.md`) as hard acceptance criteria for every implementation
prompt in this project:

```text
Real        — Agent C performs actual INSERT/UPDATE/DELETE operations.
Local       — the whole environment runs on one machine.
Isolated    — dedicated networks, synthetic data, no host access.
Auditable   — every delegation, credential, decision, and mutation is
              recorded with actor, time, and before/after state.
Repeatable  — same seed, same trigger, same agents, same profile,
              runnable over and over.
Reversible  — one command (`make reset`) restores full baseline state.
```

A prompt or an implementation choice that weakens any one of these six
properties to make something easier to build should be treated as a
design regression, not a reasonable trade-off — flag it and revisit the
relevant prompt rather than shipping it silently.
